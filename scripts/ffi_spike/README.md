# In-process AOT worker spike

This experiment runs the BRA scheduler as a Rust shared library on a native
thread. The Dart AOT host starts the generated builder catalog in an isolate
when Rust first needs a worker. Each endpoint sends the existing protocol v1
frames through memory queues. Dart uses asynchronous FFI listener callbacks to
wake the host and worker. Asset RPC, frame encoding, and the existing output and
graph transaction all exercise the same handlers as the pipe worker.

The spike runs one single-package build per host invocation. Each worker has a
separate AOT isolate, connection ID, and queue. The standard BRA executable
uses its existing pipe transport. The optional direct reader waits on the Rust
queue notification and decodes an owned frame in Dart, keeping the same
encoding and one native-to-Dart copy.

The parallel spike requires the shared Analyzer byte store and directive
dependency cache to be disabled. Their Unix file locks serialize processes.
Multiple isolates in one process need additional coordination to share those
stores. The benchmark warms the SDK summary in a separate single-worker build
and uses that existing summary in both lanes.

## Reproduce on Linux

Use the same Dart SDK for host and worker compilation. Run from the spike
checkout with the Dart and Cargo toolchains available:

```sh
dart pub get
cargo build --release --locked --manifest-path rust/Cargo.toml --bin build_runner_accelerator
cargo rustc --release --locked --manifest-path rust/Cargo.toml \
  --lib --features ffi-spike --crate-type cdylib

python3 scripts/ffi_spike/benchmark.py \
  --dart "$(command -v dart)" \
  --native rust/target/release/build_runner_accelerator \
  --library rust/target/release/libbuild_runner_accelerator.so \
  --jobs 4 --fixtures mixed_application --features 100 \
  --sample-memory --ffi-reader direct \
  --results /tmp/bra-ffi-benchmark
```

Use `--ffi-reader stream` for the original FFI reader. The results directory
must be new. Pass `--offline` when the fixture
dependencies are already cached. The harness checks source and cached generated
files against stock build_runner for clean, no-op, one-file, and broad edits. It
runs three samples per case and alternates the order of the two BRA lanes.
Timing starts with precompiled AOT workers. The pipe lane invokes the native CLI
directly with supervision disabled, while the FFI lane invokes the AOT host.
Clean samples remove the graph and generated outputs after warming the
manifest and SDK summary. An extra broad build per lane
captures worker metrics separately from the timed samples. The final checks
cover lazy loading on a no-op, preservation of generated bytes and graph on
snapshot startup failure, and a successful retry with worker PID and connection
tracing. A separate reset probe starts all FFI workers before the first phase
so the real overlay reset is delivered to every isolate. The mixed fixture
also checks SIGTERM after worker attachment and a successful subsequent build.

`samples.json` retains the command, runtime, and resource counters for every
sample. The peak RSS counter is the largest reported process high-water mark.
Use `--sample-memory` to sample Linux RSS and PSS across the isolated process
session at 10 ms intervals, separately from the wall-time samples. PSS
apportions shared memory across processes.

## Initial single-worker results on main at 7df5fae

These measurements used the initial spike and enabled the shared caches.

Linux x64, Dart 3.13.3, Rust 1.98.1, build_runner 2.16.2, one job,
and a two-CPU quota. Times are milliseconds, median [minimum–maximum],
from three samples per cell. All 48 builds matched stock byte for byte
across source and cache outputs. The Riverpod fixture had 6 generated
files and JSON Serializable had 200. Worker traces showed distinct scheduler
and worker PIDs for the pipe lane and a shared PID for FFI. Both fixtures passed
the missing-snapshot and retry checks.

| Fixture | Case | Pipe | FFI | Median change |
| --- | --- | ---: | ---: | ---: |
| Riverpod | Clean | 291.9 [238.9–327.4] | 282.3 [281.5–313.0] | −3.3% |
| Riverpod | No-op | 10.7 [10.2–12.1] | 12.8 [12.1–17.3] | +2.1 ms |
| Riverpod | One file | 235.9 [235.5–292.9] | 220.4 [217.4–240.9] | −6.6% |
| Riverpod | Broad | 264.3 [249.7–296.9] | 228.2 [205.5–233.5] | −13.7% |
| JSON Serializable (100) | Clean | 472.2 [434.4–580.1] | 449.7 [434.9–476.1] | −4.8% |
| JSON Serializable (100) | No-op | 13.1 [11.3–13.2] | 17.4 [16.3–18.0] | +4.3 ms |
| JSON Serializable (100) | One file | 137.8 [126.4–189.8] | 126.1 [112.8–129.4] | −8.5% |
| JSON Serializable (100) | Broad | 520.3 [509.0–548.2] | 471.4 [446.8–522.2] | −9.4% |

In the broad diagnostics both lanes serviced 73 asset requests for Riverpod
and 305 for JSON Serializable. Rust's recorded asset RPC handling was higher
with FFI in these two diagnostic runs (3.9 to 8.6 ms and 5.2 to 22.0 ms).
The wall-time comparison measures the whole change, including worker startup,
the Dart host, and channel scheduling. The experiment retains serialization
and copies the frames through the FFI boundary.

The median process high-water mark for broad builds was 76,068 to 84,372 KiB
for Riverpod and 67,988 to 78,060 KiB for JSON Serializable. Aggregate memory
and the effect of parallel workers remain open. The measured benefit supports
testing a larger multi-worker build before changing BRA's default transport.
Watch, signal cancellation, cold AOT compilation, and other SDKs and operating
systems remain outside the measured scope.

## Four-worker comparison

The generated mixed application has 100 features and uses Freezed, Riverpod,
and JSON Serializable. This run used Linux x64, Dart 3.13.3, Rust 1.98.1,
`--jobs 4`, and a two-CPU quota. Both shared caches were disabled for all lanes.
Builds used precompiled AOT workers and the warmed manifests and SDK summaries.
The stream and direct FFI readers used the same snapshot and warmed workspace.
All six permutations of lane order ran once. Each of the 72 builds matched
all 403 source and cache outputs from stock build_runner.

Wall time is in milliseconds, median [minimum–maximum], six samples per cell.

| Case | Pipes | FFI stream | FFI direct |
| --- | ---: | ---: | ---: |
| Clean | 3470 [3392–3628] | 3484 [3306–10861] | 3393 [3311–3497] |
| No-op | 33.2 [32.0–37.0] | 35.2 [33.0–38.1] | 36.9 [33.3–42.9] |
| One file | 790 [780–878] | 762 [714–889] | 760 [693–826] |
| Broad | 3609 [3293–3759] | 3374 [3225–3514] | 3435 [3252–3777] |

The preceding three-repeat experiment with the stream reader measured 726 to
776 ms for the one-file edit and 3319 to 3351 ms for the broad edit. The first
stream clean sample in the six-repeat run took 10.86 s and is included in the
range. The timing results vary between runs, especially for the one-file edit.

Separate diagnostic runs gave the following sampled whole-session peak PSS.
The broad pipe run reached five processes, including the native scheduler,
and each FFI run used one process with four workers. The no-op lasted too
briefly for a useful peak PSS comparison.

| Case | Pipes | FFI stream | FFI direct |
| --- | ---: | ---: | ---: |
| One file | 115.9 MiB | 117.9 MiB | 120.4 MiB |
| Broad | 290.1 MiB | 291.8 MiB | 304.3 MiB |

In the one-file diagnostics, the summed worker-side frame processing timer
fell from 4.4 to 1.5 ms and the Rust-to-Dart enqueue-to-take time was 23.1
versus 22.2 ms. For broad edits these were 17.4 to 7.0 ms and 55.3 versus
57.5 ms. These counters sum stages across workers. In both no-op diagnostics
the host opened the shared library in about 0.45 ms, Rust's build span ran for
about 34 ms, and the host spawned zero isolates.

The separate reset probe kept all four FFI isolates live before producing
the first overlay. Four connections acknowledged the normal overlay reset
under one PID and generated the stock bytes. In the usual cache-disabled
schedule, the builders using the resolver use one worker early and the
pool reaches four later. SIGTERM after worker attachment kept the last
committed graph and outputs byte-identical. A subsequent invocation
reacquired the workspace lock and matched stock again.

The direct reader reduces frame processing. Its end-to-end medians track the
stream reader closely and the broad-memory sample was higher. Cross-isolate
cache coordination and comparison on a larger CPU quota take priority over
further frame optimization. Watch and cold concurrent SDK summary generation
remain outside the validated scope.
