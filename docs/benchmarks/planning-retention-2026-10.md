# Action planning ownership comparison (2026-10-07)

Base: main `cda5219`. Linux x86_64, pinned Rust 1.98.1, release test profile.
Dart compatibility checks used SDK 3.13.3 and one worker.

## Ownership change

Each configured builder entry with inputs owns one immutable `BuilderInstance`
through `Arc`: effective definition, target, package, root flag, resolved phase,
instance key, options and part-directive suffix. Entries are never pooled by
factory ID, so runtime mappings and options stay distinct across targets/phases.
Each action owns its input and output list once in `Arc<BuildAction>` (`BuildSpec`).
Dirty lists, phase lists, optional-output indexes and lazy results clone handles;
the dirty dependency lookup borrows handles from the plan.

The instance-key and action-key expressions and enumeration loops are unchanged.
Handles refer directly to allocations, not positions in a reorderable vector.
All ownership ends with the build's local plan, dirty lists, index and lazy state;
resident workers retain neither handle type. A Weak-based regression checks
release after the last local owner drops. Empty configured entries allocate no
instance. Request serialization still owns the same IPC values; graph and IPC
formats are unchanged.

## Isolated measurement

`planning_retention_benchmark` creates four configured entries: one factory on two
targets/three phases, plus an optional builder. Each has a distinct runtime
mapping, two outputs per input, and nested options with a 1 KiB string. The state
is empty (clean planning/dirty pass), and outputs are absent. The benchmark times
planning separately from planning + dirty analysis + optional index construction.
It runs no worker and writes no generated outputs. Untimed JSONL dumps compare
all action identities, inputs, outputs, options, root/phase/part metadata, action
order, dirty order, lazy-force keys and output-index mappings byte for byte.

Seven alternating main/candidate pairs per size; caches and toolchain shared.
CPU is user + system time for the entire Rust test process, including fixture
setup, teardown and the test harness. Peak RSS is the Linux child-process high
water mark from `resource.getrusage`; it includes the process launch floor and
is not an allocation counter. Small-process RSS cannot resolve the Arc cost.
The shared execution environment introduces timing noise; these are scoped
fixture measurements, not end-to-end build speed or general memory guarantees.

| Actions | Lane | Planning ms | Planning + dirty + index ms | Process CPU ms | Peak RSS KiB |
| ---: | --- | ---: | ---: | ---: | ---: |
| 80 | main | 0.803 | 1.557 | 3.443 | 8,576 |
| 80 | candidate | 0.540 | 1.033 | 3.323 | 8,576 |
| 20,000 | main | 227.852 | 355.888 | 466.821 | 154,300 |
| 20,000 | candidate | 169.054 | 229.252 | 289.236 | 38,764 |

All entries are medians. Large-fixture planning ranges: main 212.075–236.812 ms,
candidate 154.057–198.486 ms. Small-fixture planning ranges: main 0.683–1.106 ms,
candidate 0.508–2.579 ms; the tiny case remains noisy. No median regression was
observed in this small fixture, but it does not isolate reference-count cost.
One Arc allocation per action and atomic increments on handle clones are new
costs; per-action metadata and deep spec copies are the removed retained data.
Allocation counts and individual overheads were not measured. These clean-pass
numbers do not establish no-op or incremental speedups.

Reproduce using a disposable baseline checkout (the adapter only transplants
fixture/benchmark code and a copy of the existing optional-index expression):

```bash
git worktree add --detach /tmp/planning-main cda5219
python3 scripts/benchmark_plan_retention.py --prepare-baseline /tmp/planning-main
cargo test --release --locked --manifest-path /tmp/planning-main/rust/Cargo.toml --no-run
cargo test --release --locked --manifest-path rust/Cargo.toml --no-run
python3 scripts/benchmark_plan_retention.py \
  --baseline-bin /tmp/planning-main/rust/target/release/deps/<test-executable> \
  --candidate-bin rust/target/release/deps/<test-executable> \
  --inputs 20 5000 --repeats 7
```

Use the test executable printed by each `cargo test --no-run`, and the same
`CARGO_HOME`, `RUSTUP_HOME` and pinned toolchain for both. The adapter is for this
base revision, which supplies the shared dirty-test helpers. Raw JSONL contains
per-run samples and summaries; keep it local.

## Correctness verification

- `cargo fmt --all --manifest-path rust/Cargo.toml -- --check`
- `cargo clippy --locked --manifest-path rust/Cargo.toml --all-targets --all-features -- -D warnings`
- `cargo test --locked --manifest-path rust/Cargo.toml`: 114 passed, one ignored benchmark.
- `bash scripts/correctness_arbitrary_dependency_target.sh`: same factory on
  multiple targets, dependency-owned targets, cache outputs and incremental
  generated bytes match stock.
- `bash scripts/correctness_optional_builder.sh`: stock/native equality for
  demand/no-demand, no-op, incremental, failure recovery, delete and rename.
- Separate disposable large fixture: copied `arbitrary_builder_app`'s echo
  builder and pubspec, selected only `lib/input_*.txt`, supplied a suffix option
  and an unused 1 KiB option, and generated 20,000 numbered text inputs. Main
  built 20,000 actions; candidate rebuilt all actions after removing the
  40,000 `.gen.txt`/`.meta.txt` files. SHA-256 maps of all output paths/bytes
  matched. Debug frontends, one JIT/kernel worker, shared Dart/package cache;
  this was an untimed correctness check, not a performance comparison.

`benchmark_optional_builder.sh` completed stock/native clean builds but failed
its no-op stdout grep: `worker_run_frontend` captures stdout in its verification
log. The correctness script checks that log and passed the no-op case. The
benchmark harness was left unchanged. Broad verification/watch suites remain
for CI as requested.
