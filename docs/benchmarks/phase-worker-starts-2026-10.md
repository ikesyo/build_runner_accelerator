# Phase worker startup comparison (2026-10-08)

Base: latest main `6a6913a`. Linux x86_64, Rust 1.98.1 release profile,
Dart 3.13.3, build 4.0.10 and build_runner 2.16.1; one SDK/pub cache for
stock and both native lanes. CPU quota: `200000 / 100000` (two CPUs).
Cgroup memory limit: 8 GiB. At the separate diagnostic run's start,
cgroup usage was 834,543,616 bytes and available memory was 7,755,390,976
bytes (minimum of host MemAvailable and cgroup headroom). This is a shared
execution environment, not an otherwise idle benchmark machine.

## Change and synchronization

Calculate participants before growing the pool: request count and `--jobs`,
then the existing resolver cap for homogeneous resolver-backed or unclassified
batches with shared caching enabled. The default cap remains
`max(ceil(jobs/2), min(2, jobs))`; explicit cap values clamp to jobs, and `0`
removes the resolver cap. Known non-resolver/mixed/post-process batches keep
the existing unrestricted policy. With shared caching disabled, the first
unclassified homogeneous batch and known resolver batches stay on one worker;
classification still only promotes to resolver use. Optional/nested work
remains serialized. There is no new scheduler or automatic jobs policy.

Only new workers receive a bootstrap reset after normal initialization. Its
source/cache update lists cover the current overlay; deletion lists cover the
transaction's deleted assets, including stale outputs awaiting regeneration.
Locations come from the current visibility index, including previous graph
outputs. Unknown deleted locations use the source list; Dart applies both lists
to the same invalidation view. One immutable existing-format blob transports
the current bytes, even for one joining worker. No old reset history or bytes
are retained. Join all responses before dispatch and keep the blob alive until
then. A failed publication/reset leaves workers pending for retry. Normal
blocked-asset checks, dependency recording, output validation and atomic commit
are unchanged. Resident workers do not shrink/restart between phases; watch
resets, artifact pinning/upgrades and initialization signatures are unchanged.

## Fixture and verification

`scripts/check_phase_worker_growth.py` creates eight Dart inputs. An Analyzer
builder emits cache `.cache.dart` files; a later Analyzer builder resolves
those files and emits source `.ready.dart` files. Both assert their own
same-phase output is unreadable, including stale on-disk outputs. A final
post-process phase reads generated source inputs on additional workers and
emits `.done` files. Source/cache/dynamic output hashes are checked against stock
after clean, no-op, one-file, broad and deletion (producer emits no output).
Failure leaves generated bytes and graph unchanged; recovery matches stock.
The initial output set contains 24 files; deletion removes all three outputs
for input zero. The fixture is deliberately small and uniform.

- `cargo fmt --all --manifest-path rust/Cargo.toml -- --check`
- `cargo clippy --locked --manifest-path rust/Cargo.toml --all-targets --all-features -- -D warnings`
- `cargo test --locked --manifest-path rust/Cargo.toml`: 116 passed, one ignored.
  A control-worker regression reads live snapshot blobs, checks source/cache
  updates and deletions, rejects bootstrap resets, retries, verifies existing
  workers receive no bootstrap, and checks retention and next-build reset.
- Fixture runs: jobs 1/2/4 with the default shared-cache policy; jobs 4 with
  cap 1 and cap 0; jobs 1/2/4 with shared cache disabled. All compared bytes
  match stock. Diagnostic runs are separate from speed samples.
- `bash scripts/correctness_optional_builder.sh`: passed demand/no-demand,
  chained optional outputs, no-op, incremental, atomic failure recovery,
  deletion and rename comparisons with stock (default serial optional route).

An initial fixture sequence also found an existing main limitation: after
deleting input zero's generated outputs, failing and then recreating it,
main runs the two normal actions but misses its post-process action on the
first recovery build. This is outside worker startup changes. The successful
comparison orders failure/recovery before deletion; it does not claim coverage
of that failing delete/recreate sequence. Broad watch, platform, dependency,
optional and lifecycle matrices remain CI work.

## Measurements

Two alternating pairs per jobs value, metrics/trace disabled. Commands invoke
the native frontend directly, excluding the Dart launcher. Manifest, worker
AOT and SDK summary are prepared outside timing. Both lanes use the same
fixture and cache paths; graph/output and analyzer byte/dep caches are cleared
before each clean series, then no-op and real edits reuse that series' caches.
SDK/pub caches and OS page cache are warm. Preparation and stock timing are
excluded. Extra diagnostic/correctness processes did not run CPU work during
the speed samples.

Entries are main / candidate medians. CPU is user + system for the frontend
and waited descendants, measured via RUSAGE_CHILDREN deltas. RSS is the peak
**simultaneous sum** sampled from the frontend's process tree every 20 ms;
shared pages are counted per process, so this is neither PSS nor private
memory. Short peaks/children can be missed. It is not maximum single-process
RSS presented as worker-total memory. No-op RSS samples missed most or all of
the process lifetime. Wall time includes polling/scan overhead; very short
no-op wall times approach the polling floor.

substantial noise despite unchanged startup counts. No speedup is claimed.

Separate clean diagnostics at jobs 4:

| Policy | Candidate phase participants / resident counts | Main → candidate starts / initializations | Main → candidate resolver resets |
| --- | --- | --- | --- |
| default shared | 2/2, 2/2, 4/4 | 4/4 → 4/4 | 8 → 6 |
| cap 1 shared | 1/1, 1/1, 4/4 | 4/4 → 4/4 | 8 → 5 |
| cap 0 shared | 4/4, 4/4, 4/4 | 4/4 → 4/4 | 8 → 8 |
| shared disabled | 1/1, 1/1, 4/4 | 4/4 → 4/4 | 2 → 5 |

Main's default resolver phases use two of four resident workers; candidate
starts only two there, then starts/initializes two more at the final phase.
Default bootstrap wall time was 9.947 ms, including snapshot spool/encoding
and joined reset responses; cap 1 was 9.294 ms. No bootstrap is needed with
cap 0 or jobs 1/2 under the default policy. Summed default worker initialization
time was main 66.845 ms / candidate 91.931 ms (separate diagnostics, not timed
speed samples). Final startup totals are unchanged in this widening fixture:
the benefit is avoiding earlier idle workers and their earlier phase resets,
while the additional synchronization is a real cost. These results do not show
that the savings outweigh that cost for this workload.
With shared caching disabled, main already delays expansion until the final
phase; candidate additionally fixes the missing state synchronization there.
That policy has no startup reduction in this fixture and adds three resets.

Weighted partitioning, dynamic scheduling and automatic cache sizing remain
separate candidates. This small uniform fixture provides no useful evidence
for a long-tail action imbalance or a cache-capacity problem. Measure larger
heterogeneous workloads before choosing any of them; no timing cache is added.

Reproduce with two release binaries built from main and this branch:

```bash
python3 scripts/check_phase_worker_growth.py \
  --baseline /tmp/phase-worker-main/rust/target/release/build_runner_accelerator \
  --candidate rust/target/release/build_runner_accelerator \
  --dart .toolchains/dart/dart-sdk/bin/dart \
  --output /tmp/phase-growth-speed --jobs 1 2 4 --repeats 2
python3 scripts/check_phase_worker_growth.py \
  --baseline /tmp/phase-worker-main/rust/target/release/build_runner_accelerator \
  --candidate rust/target/release/build_runner_accelerator \
  --dart .toolchains/dart/dart-sdk/bin/dart \
  --output /tmp/phase-growth-diagnostics \
  --reuse-fixture /tmp/phase-growth-speed/app --jobs 4 --repeats 1 --metrics
```

Repeat diagnostics with `--cap 1`, `--cap 0`, or `--shared-cache 0`.
Raw speed/diagnostic JSON and logs are local `/tmp/phase-growth-*` artifacts,
not checked in. The script records commands, SDK/binary/builder identities,
quota, memory headroom and cache policy with new runs. The local speed run used
the already prepared `/tmp/phase-growth-speed2/app` after an initial harness
attempt, with successful samples/logs under `/tmp/phase-growth-speed3`.
