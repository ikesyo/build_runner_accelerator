# Cold build: measured Builder asset lookup costs

## Scope and conditions

Baseline: latest main `ebea364` (PR #82 included). Linux x64, Dart 3.13.3,
Rust 1.98.1, two-CPU cgroup quota (`200000 100000`), 8 GiB memory limit.
No large application checkout is available here. The 10- and 500-input JSON
fixtures are synthetic; these results do not establish a speedup for the
reported 75-second application.

All paired runs use the same fixture working directory, SDK, package
configuration, worker count and actual cache directory
`/workspace/cold-investigation/cache` on `/workspace`. Order alternates AB/BA,
seven repeats per lane and worker count. Single-flight is disabled. Timings
exclude metrics/trace logging and concurrent compilation or verification.
AOT workers are prepared separately from main and the candidate with the same
SDK and fixture package configuration. Explicit worker paths exclude AOT
compilation and artifact validation; the native frontend is invoked directly,
excluding the Dart launcher.

Cold empties `byte_store` and `dep_parse`, removes generated sources/cache
parts and `graph-v3.bin`. Warm clean removes outputs and graph but retains
shared caches. No-op follows warm clean. One-file and broad cases rename a
model field and therefore change generated bytes. SDK summaries in each
fixture's `.dart_tool/build_resolvers` are retained and warm;
`ANALYZER_STATE_LOCATION_OVERRIDE` is set but is **not** build_runner's
SDK-summary location. SDK/pub dependencies and OS page cache remain warm;
OS caches are not flushed. These are build-cache-cold results, not
machine-cold results.

## Bottleneck investigation

Three main-only diagnostic cold samples per worker count separate
`TimedActivity.analyzing`, cycle walks, SDK/driver initialization, cache
access and Builder time. Activity buckets and method timers overlap and
must not be summed as independent stages.

At 500 inputs / four requested jobs, a representative run has 1.070s
aggregate JSON Builder time (including 0.336s Analyzer activity), 0.271s
combining Builder time, 0.074s first resolver initialization, 0.081s cycle
walking, 0.031s dependency parsing and 0.033s byte-store writes. Reads take
less than 1ms. The combining Builder alone spends 0.085s waiting for glob
RPCs and 0.033s on can-read RPCs. Rust records 0.077s aggregate resolver
reset time; concurrent resets mean this is not wall time.

| Inputs | Jobs | Main diagnostic cold median | Child CPU median |
| ---: | ---: | ---: | ---: |
| 10 | 1 | 0.1049s | 0.1037s |
| 10 | 2 | 0.1219s | 0.1905s |
| 10 | 4 | 0.1142s | 0.1961s |
| 500 | 1 | 1.5444s | 1.5920s |
| 500 | 2 | 1.0568s | 1.6458s |
| 500 | 4 | 1.0928s | 1.7085s |

The 500-input fixture benefits from two resolver workers; the 10-input
fixture pays mostly fixed startup/driver costs. Four requested jobs retain
the existing two-worker resolver cap. The implementation does not change
that policy or enable single-flight.

A detailed four-job probe before positive glob caching observes two active
resolver workers, each with 500 actions invoking `libraryFor` across both phases,
512 distinct Analyzer file-content paths, one driver creation and zero
resolver replacements. Twelve file-content paths and five `.linked`
cache-miss keys overlap between workers. A miss key describes an Analyzer
bundle/cycle, not a count of parsed libraries; a file-content callback does
not prove linking. This small closure does not justify a new cross-worker
analysis policy. Per-worker RSS peaks are 88.5 and 89.1 MB. These values and
the 8 GiB limit give no evidence of memory pressure in this fixture.
The existing driver/context survives actions and the generated-output phase
reset; there is no measured context-lifetime issue to fix here.

A separate candidate trace reports 502 total uncached `can_read` RPCs,
versus 1,002 before positive glob caching: the 500 combining-Builder requests
are eliminated. The two active workers use 0.64s / 0.66s CPU, peak at 103.7MB / 102.8MB RSS,
and accumulate 0.604s / 0.590s action wall time. Each executes 500 actions.
Their similar work totals show no meaningful assignment imbalance here.
The parallel action stage lies on the critical path; the action sums exclude
phase resets, native commit and startup, and do not add to build wall time.
Two spare workers have no action traces;
aggregate child CPU in the timing harness includes their startup work.

Instrumentation is measurable: three candidate cold probes per mode, with
order reversed on alternate repeats, have elapsed medians of 0.833s with
metrics disabled, 0.942s with ordinary metrics, and 0.949s with detailed
traces. These are separate diagnostic samples, not a main/candidate speedup
comparison. The ~13–14% observed overhead is why all paired timings above
disable both instrumentation modes.

## Adopted changes

- Narrow ordered overlay and optional-output maps to the package and the
  glob's literal prefix before glob/visibility checks. This avoids scanning
  every overlay key for each narrow combining-Builder glob. Matching,
  visibility, existence and output commit rules remain unchanged.
- Add visible glob results to the existing positive readability cache. Rust
  already checks existence and phase visibility for these results.
  Subsequent `canRead` calls still record reads and check current action
  visibility before using the cache. Byte reads, reset/deletion invalidation
  and optional-builder demand remain on their existing paths.
- Add opt-in path/cache-miss diagnostics, worker PID/RSS, driver
  creation/replacement counts and Linux CPU ticks. Detailed traces require
  `BUILD_RUNNER_ACCELERATOR_METRICS=1` and
  `BUILD_RUNNER_ACCELERATOR_ANALYSIS_TRACE=1`; they are excluded from timing
  comparisons. CPU ticks are cumulative user + system CPU, converted using
  `getconf CLK_TCK` (100 here).

The prefix-only experiment did not give a consistent whole-build improvement
at every worker count, so it was not used alone as evidence of success.
The follow-up path probe identified 500 extra combining-Builder `can_read`
requests. The combined implementation is measured below. No ADR is needed:
this narrows existing searches and reuses the existing positive cache without
changing a protocol, scheduler, phase or commit boundary.

## AOT-inclusive first execution

Three alternating samples per lane use normal worker preparation and validate
generated-source/cache-part equality. All logs show a newly compiled AOT worker;
none falls back to JIT. SDK summaries, pub dependencies and OS pages are retained.
A brief benchmark-helper test overlapped the last original 500-input pair; that
pair is excluded and replaced by an uncontended AB pair.

| Inputs | Main median (min–max) | Candidate median (min–max) |
| ---: | ---: | ---: |
| 10 | 28.678s (28.277–29.245) | 28.306s (28.108–28.406) |
| 500 | 29.144s (28.525–29.419) | 29.744s (28.716–29.818) |

The approximately 28–30s preparation cost dominates both sizes. These samples
do not establish an AOT-inclusive first-execution speedup. The measurable gain
is in the build-cache-cold, AOT-prepared stage.

## Reproduction

Use disposable fixture/cache directories. The harness temporarily edits
fixture fields and restores original source bytes in `finally`. Resolve the
fixtures offline outside timing. Build release main/candidate frontends with
the same Rust toolchain. Compile each worker **with its fixture package
config**: AOT programs retain that identity, so a ten-input worker cannot be
reused for the differently named 500-input package. Place workers under the
fixture's `aot-sdk/bin`, with `lib` and `version` pointing to the selected
SDK, as the normal frontend prepares them.

```bash
python3 scripts/benchmark_cold_build.py \
  --baseline /path/to/main-frontend --candidate /path/to/candidate-frontend \
  --frontend-dart /path/to/sdk/bin/dart \
  --worker /path/to/fixture/aot-sdk/bin/main-worker \
  --candidate-worker /path/to/fixture/aot-sdk/bin/candidate-worker \
  --root fixtures/json_serializable_500_app \
  --cache /path/to/disposable-cache --results /path/to/results \
  --jobs 1 2 4 --repeats 7

# Separately include manifest/kernel/probe/worker compilation.
python3 scripts/benchmark_cold_build.py \
  --baseline /path/to/main-frontend --candidate /path/to/candidate-frontend \
  --frontend-dart /path/to/sdk/bin/dart \
  --baseline-package /path/to/main-checkout --candidate-package "$PWD" \
  --aot-cold --root fixtures/json_serializable_500_app \
  --cache /path/to/disposable-cache --results /path/to/initial-results \
  --jobs 4 --repeats 3
```

Repeat for `json_serializable_10_app`. Keep summary files in
`.dart_tool/build_resolvers` to reproduce this report; deleting them measures
an additional SDK-summary-cold condition. `--metrics` produces separate
diagnostic samples. Never combine trace-enabled runs with metrics-disabled
elapsed-time results.

The harness records commands, SDK, binary/worker hashes, paths, child CPU,
maximum individual process RSS and output hashes in `metadata.json` /
`builds.json`, plus all samples in `summary.json`. Maximum process RSS is
not summed worker RSS. Raw local artifacts are under
`/workspace/cold-investigation/{final-10,final-500,initial-10,initial-500,one-file}`.
The checked-in summary retains every paired timing sample. No public
launcher-inclusive benchmark claim is made.

## Verification and limitations

All 98 Rust tests and 141 Dart tests pass, including the new ordered-map
equivalence/updates and positive-glob visibility/read-tracking regressions.
Five release-downloader tests initially required loopback access; their
network-enabled rerun passes. Static analysis and the four existing benchmark
timeout/cleanup helper tests pass. Integration verification is bounded and
the PR CI supplies the full compatibility/lifecycle/watch coverage.
Commands: `cargo test --offline --locked --manifest-path rust/Cargo.toml`,
`dart analyze lib bin test tool`, `dart test`, and
`python3 -m unittest discover -s scripts -p test_benchmark_shared_byte_store.py`.
Single-flight remains disabled. Parallel processing, published cache
visibility, cache fault fallback and transactional graph/output commit code
are unchanged. Large-app Analyzer dominance, dependency-aware placement and
AOT-inclusive speedup are not established by these measurements.
