# Phased cycle dependency reads (2026-10-05)

Baseline: main `202eed0` (also v0.9.0); `git fetch origin main --tags`
completed before branch creation. There were no post-0.9.0 main changes to
repeat. Existing PRs #84/#85 already cache conditional directive extraction
and the collector's exact-byte SHA-256. This experiment does not repeat them.

## Diagnostic evidence and code boundaries

The supplied 0.9.0 anonymized regen trace has 3,133 actions and 20,082 cycle
file loads. Worker sums are `cycle_graph_walk_us=5,789,768`,
`dep_read_phased_us=4,105,599`, `dep_prefetch_us=1,195,106`,
`ipc_resolve_assets_us=864,775`, and `apply_pending_changes_us=1,624,256`.
Cycle directive cache hits/misses are 14,723/1. Under that loader's enabled
cache, each nonempty phased value contributes one hit or miss: 14,724 nonempty
loads and 5,358 empty loads account for the 20,082 total. This is not proof
of same-version positive duplication; the old trace has no per-load content
version/phase records. Per-PID maxima of cumulative
`driver_creations` are 1/1/0/0: **two creations**, not 2,808; all resolver
replacement counts are zero. The provided report's driver interpretation is
incorrect. The private application sources are unavailable here.

The cycle loader calls `readPhased`, wraps parsed dependencies, then prefetches
complete results' dependencies. `dep_read_phased_us` includes current
readability, content acquisition, conversion/hash, BuildState update and
Analyzer notification. **Prefetch is outside that timer**, inside the cycle
walk; its RPC time is inside its own total. `applyPendingFileChanges` runs
later. These worker sums and nested timers must not be added or converted into
wall-time savings.

| Boundary | Probe and meaning |
| --- | --- |
| Current visibility | `dep_visibility_us`: `canRead`, its cache/RPC and current action restrictions |
| Content acquisition | `dep_content_us`: `readContent` (baseline additionally copies bytes); existing `ipc_read_us` is the RPC subset, so the remainder can include file I/O/cache ownership |
| Conversion/hash | `dep_content_decode_hash_us`: the usual UTF-8 and content-only MD5 materialized before notification, only in diagnostics |
| Source/Analyzer update | `dep_content_update_us`: BuildState update plus replayed content listener bookkeeping |
| Dependency load result | `dep_loads`: asset, phase, actual content hash/expiry, and cache-hit/read-RPC deltas during `readPhased` |
| Parse/graph/prefetch | Directive-cache probes and `dep_prefetch_us` run after `readPhased`; graph traversal is included in `cycle_graph_walk_us` |

The probes deliberately do not attribute all action-wide read RPCs/cache hits
to dependency loads. Trace deltas isolate the byte-cache traffic inside each
phased load; prefetch warming remains a separate boundary. An unavailable load
can legitimately have neither a byte-cache hit nor a read RPC.

Positive prefetch entries populate the existing owned immutable byte cache;
negative or failed answers do not. The real `canRead`/`readContent` calls still
check outputs, blocked IDs and post-process primary inputs and record observed
reads. Optional demand declines speculative batch prefetch and uses real
sequential reads. Updated/deleted source/cache deltas remove affected byte and
readability entries before a resolver reset; full build/failure recovery clears
all entries. Unchanged byte snapshots may survive phase resets. A directive
change clears the cycle graph; expired unavailable values reload at later
phases regardless of graph retention.

The existing dep path then copies owned `Uint8List` bytes through the public
`readAsBytes` API into a generic `List<int>`, creates `AssetContent`, and
decodes/hashes it for the Analyzer. That second copy serves no builder caller:
the dep loader only consumes strings and its content listener reads the bytes.
It also prevents UTF-8's typed-buffer path. The candidate uses
`readContent(id).bytes` directly **only for phased dep content**, replaying both
updates with a fresh `AssetContent`. Public `contentOf` and builder byte reads
retain their mutable copies. No read, validation, hash, graph update or phase
expiry is omitted; no new conversion/digest cache, protocol or cache key exists.

## Fixture and comparison

`scripts/prepare_cycle_read_fixture.py` creates 64 mixed Riverpod/Freezed/JSON
inputs sharing 16 conditional API alternatives and 128 transitive export-chain
sources (eight chains of depth eight per alternative). These are ordinary Dart
class declarations. One-file and broad edits rename provider functions and
must change generated bytes. Stock references cover all cases, including
both `.g.dart`/`.freezed.dart` source outputs and generator cache parts.

Linux container: 2 CPU quota, 8 GiB memory; Dart 3.13.3, Rust 1.98.1,
Analyzer 14.3.0, build_runner 2.16.1, same pub cache/lockfile and native release
executable. Jobs=2/4 are explicit; jobs=4 does not mean four physical CPUs.
The Rust code is unchanged, so both lanes use the same executable. Baseline
workers are compiled from an untouched archive of `202eed0`, candidate workers
from the work branch, into the same fixture SDK layout. Diagnostic baseline
workers additionally have identical boundary probes and the original copying
content path; they are never used for speed comparisons. Apply
[`baseline-diagnostic.patch`](baseline-diagnostic.patch) to a separate main
archive for those diagnostics; keep the untouched archive for timings.

Prepared comparisons clear byte-store and directive caches for `cold`, keep
prepared worker/SDK summaries, and then run `warm-clean` (regen), `no-op`,
`one-file`, and `broad`. Full AOT cold runs additionally remove workspace
accelerator state and worker/kernel/probe shared caches and include preparation.
SDK summaries and OS page caches remain warm; pub resolution is untimed.
Baseline/candidate order alternates by repeat in each worker-count group.
Metrics and trace are **disabled** for speed runs; diagnostics are separate.
Commands, artifact/config/input hashes, output hashes, raw samples and
median/min/max are recorded by `benchmark_cold_build.py`.

Warm-clean has identical measured load/read counts in both lanes/jobs:
1,226 cycle loads, 842 positive values and 384 unavailable values. Positive
worker/asset/content versions are all unique: **zero repeated positive version
loads within a worker**, including across phases. 357 versions are loaded by
both analysis workers; each independent driver needs its own filesystem/graph.
778 positive loads hit the existing byte cache, transferring 4,668,624 bytes;
64 use committed overlay content. There are **zero byte-read RPCs inside these
phased loads**. The baseline nevertheless spends ~48–51 worker-ms in content
acquisition, dominated by the redundant generic-list copy. Typed snapshots
reduce that stage to <1 worker-ms and also reduce UTF-8/hash cost. The overall
phased-read stage falls by 64.7%/71.5% at jobs=2/4. These are diagnostic stage
improvements, not application wall-time percentages.

Unavailable records are phase-dependent generated parts: phase 0/1 each has
128 empty `.g.dart`/`.freezed.dart` reads, phase 2/3 each has 64 empty `.g.dart`
reads. 128 worker/asset pairs are retried across phases. The 64 `.freezed.dart`
values become positive at phase 2 after their producer; the other 778 positives
are loaded at phase 0. Their negative answers are not byte-cache misses that
can safely be retained forever or skipped later. Real visibility checks and
read recording are preserved. Empty content also retains expiry, as do invalid
UTF-8 values. Trace hashes/expiry, not only AssetId, are used for this analysis.

One-file has 365 cycle loads: 359 positive, six unavailable; 358 byte-cache hits
(2,293,377 bytes), one committed value, and zero phased byte-read RPCs. Positive
versions are again unique within its single analysis worker. Its phased-read
worker sum falls ~77%; conversion-result retention would have no measured
positive hits here and was not adopted. Warm-clean uses two drivers and
one-file one driver; counts are per-PID **maxima** of cumulative counters,
never sums of action rows. All resolver replacement counts are zero.

The existing warm directive cache still has small misses (baseline jobs=2/4:
830/12 and 831/11 hits/misses; candidate: 832/10 for both). Measured parse sums
are only ~1.9–3.9 ms; their small cache-warming variation is not this change's
claimed benefit. Prefetch remains outside `dep_read_phased` and its RPC subset
inside prefetch. Both read visibility and prefetch still incur necessary
validation/warming work. Source/Analyzer notification counts are retained.

[Diagnostic samples](diagnostic-samples.json) contain all per-build worker sums,
version/load/cache counts and phase histograms; [diagnostic summary](diagnostic-summary.json)
contains medians, and [diagnostic metadata](diagnostic-metadata.json) identifies
workers/SDK/inputs. Aggregation keys positive versions by `(worker_pid, asset,
content_hash)` (and phase separately), unavailable values by `(worker_pid,
asset, phase)`, and driver creations by per-PID maximum. Cache/RPC deltas come
from each traced `readPhased` call. Median boundaries are computed separately,
so their rounded medians need not equal the median parent timer.

The supplied application trace cannot establish its own repeated positive
versions: it lacks these markers. The next diagnostic step there is to record
this trace and correlate positive reloads with graph clearing/phase resets
before considering conversion retention. Remaining fixture time includes
ordinary Analyzer conversion/hash and prefetch path/IPC/local-file warming;
those would need their own measured, visibility-preserving change. No digest
unification, negative-cache extension or resolver-worker policy is included.

## Reproduction

```bash
python3 scripts/prepare_cycle_read_fixture.py --root "$fixture"
# Resolve pub dependencies with the selected SDK/pub cache. Prepare a catalog,
# then compile its dynamic_worker.dart using baseline/candidate package roots
# in package_config.json, into fixture/aot-sdk/bin with SDK lib/version links.
python3 scripts/benchmark_cold_build.py \
  --baseline "$native" --candidate "$native" --frontend-dart "$dart" \
  --root "$fixture" --cache "$cache" --results "$results" \
  --fixture-kind riverpod-cycle --worker "$baseline_worker" \
  --candidate-worker "$candidate_worker" --jobs 2 4 --repeats 3 --stock-check
# Repeat separately with --metrics --trace for per-asset/content/phase evidence.
# Use a separate fixture/results directory for --aot-cold and package roots:
# --baseline-package "$main_archive" --candidate-package "$candidate_source".
```

Verification used the SDK-bin wrapper with explicit `PUB_CACHE`, `DART_SDK`,
`RUSTUP_HOME`, `CARGO_HOME` and an external absolute accelerator cache. Commands
were `dart test --compiler=source`, `dart analyze lib bin test tool`,
`dart format --output=none --set-exit-if-changed lib bin test tool`,
`cargo test --locked`, `cargo build --locked` (debug/release), and the required
scripts in `AGENTS.md`. After the initial full-run environment failure, core
cases were rerun with `VERIFY_LEVEL=targeted VERIFY_CASES=all` plus
`correctness_built_value.sh`, and remaining scopes with
`VERIFY_LEVEL=full VERIFY_FULL_SUITES=current-codegen,compatibility-lifecycle,compatibility-graph,compatibility-mapping`.

## Limits

This is a synthetic fixture, not a measurement of the user's private Flutter
application. First positive cycle loads can benefit without any repeated
positive asset version: the redundant operation is the second byte copy.
Unavailable/generated phase retries are required. Conversion-result retention
was not justified by measured same-version graph loads and was not adopted.
Whole-build speed claims require paired timings; diagnostic worker sums alone
cannot establish an application wall-time improvement. The typed snapshot is
already resident; source updates, content notification, hashing and dependency
parsing still have their existing cost.
