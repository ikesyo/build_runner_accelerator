# ADR 0003: Worker IPC and lifecycle

- Status: Accepted
- Date: 2026-09-07

## Context

The Rust frontend must invoke ordinary Dart builders without corrupting
generated bytes or diagnostic output. JSON is convenient for control messages,
but JSON-encoded byte arrays add avoidable transfer and allocation overhead.
Analyzer state and builder resources are also expensive to recreate for every
action or watch iteration.

## Decision

Use the version 1 protocol in [protocol/v1.md](../../protocol/v1.md):

- Rust owns a child process connected through stdin/stdout pipes.
- Every message is a length-prefixed frame. Control messages use UTF-8 JSON.
- Successful asset reads use a BRAB binary frame and successful build results
  use a BRAR binary frame with JSON metadata followed by raw bytes.
- The worker must advertise asset-rpc-binary-read-v1 and
  build-result-binary-v1; JSON fallback for those successful payloads is not
  part of v1.
- Both endpoints enforce a 256 MiB complete-frame limit.
- Worker stdout is reserved for frames. Human diagnostics go to stderr.
- A worker remains resident across actions and watch builds. Resolver state can
  be reset between phases while the process and permitted build-scoped caches
  remain alive.

Rust may create a bounded pool for independent actions. Requests are batched
where the protocol and ordering allow it; worker count is a performance
choice, not a compatibility shortcut.

## Consequences

The wire contract is explicit and testable, and binary payloads avoid the
largest JSON byte-array costs. A worker that does not implement the required
capabilities is rejected rather than being allowed to produce ambiguous
results. Large single results still need a future chunking design.

Resident workers reduce repeated initialization and preserve the current
builder/resource lifetime model, but they require careful reset boundaries and
process cleanup.

## Alternatives considered

- JSON for every payload: rejected for successful byte-heavy reads and results.
- A new process per action: rejected because it amplifies startup and resolver
  costs and changes resource lifetime behavior.
- An unframed shared stdout stream: rejected because diagnostics could corrupt
  the protocol.
