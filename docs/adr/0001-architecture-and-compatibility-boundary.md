# ADR 0001: Architecture and compatibility boundary

- Status: Accepted
- Date: 2026-09-07

## Context

build_runner compatibility depends on Dart builders, BuildStep behavior,
Analyzer resolvers, package configuration, and builder-owned resource
lifecycle. Reimplementing those semantics in Rust would create a second build
system and make compatibility depend on a growing list of builder-specific
exceptions.

At the same time, filesystem scanning, incremental invalidation, action
planning, scheduling, and output commits are suitable for a native frontend.

## Decision

Split the system into a Rust frontend and a resident Dart worker:

- Rust owns workspace snapshots, dependency and glob invalidation, action
  planning, phase orchestration, scheduling, overlays, atomic commits, and
  native watch.
- Dart owns builder factories, BuildStep, AssetReader, Analyzer-backed Resolver
  work, and builder/resource lifetimes.
- Official PackageGraph and BuildConfig resolution happens in Dart. The result
  is normalized into a workspace-specific manifest consumed by Rust.
- The native frontend is enabled only for a supported manifest subset.
  auto falls back to stock Dart build_runner, rust reports an error, and dart
  always selects stock Dart build_runner.
- Stock build_runner remains the compatibility reference. Supported native
  cases must preserve generated bytes and observable incremental/failure
  behavior.

## Consequences

The Rust implementation can stay focused on the high-volume frontend work
without embedding a catalog of popular builder names. Builder packages remain
ordinary Dart dependencies. Unsupported or newly introduced build semantics
have a conservative escape hatch instead of silently using an incompatible
implementation.

The protocol and generated manifest are compatibility boundaries. Changes to
either require fixture comparisons and an explicit decision. A native build
can still pay for Dart worker startup and Analyzer work; this architecture
optimizes the frontend without promising that every build becomes native
end-to-end.

## Alternatives considered

- Reimplement builder execution and Analyzer semantics in Rust: rejected because
  it duplicates the compatibility surface.
- Keep all planning in Dart: rejected because filesystem and graph work are the
  primary native optimization target.
- Maintain a hard-coded Rust catalog of popular builders: rejected as the main
  path because it does not scale to arbitrary package configuration.
