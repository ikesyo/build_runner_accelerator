# ADR 0049: Proportional leases with action-time straggler protection

- Status: Accepted
- Date: 2026-11-13
- Amends: ADR 0046

## Context

User reports bisected a large single-package clean-build regression to the
shared adaptive input queue. Its 100ms target can keep leases at one input
when worker batch setup and IPC alone cost around 129ms. Removing the input
cap does not fix a time target smaller than the fixed cost. Synthetic cheap
fixtures did not cover this regime.

One supplied report measured a two-second target reducing clean-build leases
from 3,163 to 405, with all 828 outputs byte-identical to stock. These are
private-workload measurements, not a reproducible repository benchmark or a
speed guarantee for other projects.

## Decision

Use proportional leases for both ordinary and workspace adaptive dispatch:
`max(1, remaining / (2 * eligible_workers))`. Remove the sixteen-input cap.
After initial single-input probes, bound the proportional size by a named
two-second estimate of actual input work. An observed input cost of two seconds
or more still selects one input. This target protects against slow work; it
does not attempt to amortize fixed worker overhead by choosing a larger constant.

The worker returns each action's `execution_us` even with metrics disabled.
It excludes batch setup, dependency-graph serialization and outer batch IPC;
asset RPC waits within an action remain part of its cost. Learn from
the slowest action in a completed lease so outliers do not disappear in its
average. Keep immediate reaction to expensive samples, rapid decay on cheaper
samples and application-local learning. Diagnostic workers without action
timings use the conservative whole-round-trip-per-input fallback.

An application here is one configured builder application, not the entire
consumer app. Workspace queues are separate for each target/builder/phase;
ordinary dispatch creates a fresh queue for each configured builder's request
set. Different builders do not share learned costs. Variation among inputs of
the same builder can still make the slowest-action estimate conservative;
cheaper samples decay that estimate over subsequent leases.

Raising the old target alone still leaves at least roughly 1,600 leases for
26,000 cheap inputs with the sixteen-input cap. Pure proportional or balanced
splits amortize overhead but give up the measured slow-input protection. The
combined policy separates those responsibilities instead of using IPC time to
estimate input cost. The additive timing field changes no generated bytes,
graph identity or dirty checks.

Unexpected expensive work inside a leased batch can delay that worker until
the batch completes; the target is an estimate, not a deadline.

Do not introduce a configuration option or change worker lifecycle, phase
visibility, resolver limits or publication semantics for this tuning fix.

## Validation

Queue regression tests with action timings model thousands of cheap inputs with
both 129ms and five-second fixed lease costs. They bound dispatch count
independently of that overhead and check contiguous, complete coverage. Tests
also cover a sixteen-second outlier inside a cheap batch, proportional tail balancing and missing
timing fallback. Binary-protocol tests check preservation of action timing.
The fixed-overhead-independent lease bound applies to results carrying action
timings. The separate missing-timing test checks conservative round-trip sizing,
which does not promise the same amortization when fixed overhead is large.

The `single-large` profile in `scripts/benchmark_workspace_scheduler.py` uses
2,048 inputs, two workers and a 25ms delay per action, including a resolver
phase. Compare retained baseline/candidate release binaries under the same
SDK and caches for clean, no-op, one-file and broad edits, with stock as a
byte reference. This synthetic delay does not reproduce the private project's
fixed batch cost; actual performance still needs real-project verification.
