# Build worker IPC v1

## Version boundary

The package runtime, native frontend and custom worker must use the exact same
accelerator package version. This is a release-coupled protocol: `v: 1` names
the wire framing/operations, not cross-release compatibility. Both endpoints
reject missing or mismatched `v`; initialize/initialized additionally require
`accelerator_version` equal to their compiled package version. Required
capabilities and malformed-message checks still apply. See
[ADR 0030](../docs/adr/0030-one-zero-contract-and-disposable-state.md).

## Transport

Each message is one frame. The default control-message payload is:

1. 4-byte unsigned payload length, big endian
2. UTF-8 JSON object of that length

Successful `read` asset responses and successful build results use the required
binary payloads below. The outer length prefix and frame boundaries remain the
same.

The Dart worker reserves stdout for frames. Human-readable diagnostics go to stderr.

`AssetId` is serialized as `package|path`, for example `json_serializable_app|lib/model.dart`.

## Rust to Dart

### initialize

```json
{
  "v": 1,
  "type": "initialize",
  "accelerator_version": "<exact package version>",
  "id": 1,
  "root": "/absolute/project/path",
  "package": "json_serializable_app",
  "phase_count": 4,
  "resolver_mode": "dart_local"
}
```

The worker responds with `initialized`, the same `id`, its
`accelerator_version` and a capability list. `phase_count` is a required
positive integer; root must be absolute and match the worker workspace,
and resolver_mode must be `dart_local`.

### reset_resolver

After a source builder produces an overlay asset, Rust may send
`reset_resolver` before the next builder phase. The worker clears only the
Analyzer resolver's phase-local graph so the next resolver request can see
the overlay; the resident worker and its asset-read cache remain alive.

```json
{
  "v": 1,
  "type": "reset_resolver",
  "id": 4,
  "updated_sources": ["pkg|lib/model.g.dart"],
  "deleted_sources": ["pkg|lib/old.g.dart"],
  "updated_cache": [],
  "deleted_cache": [],
  "incremental": true,
  "overlay_blob": {
    "path": "/absolute/project/.dart_tool/build_runner_accelerator/overlay-blobs/123-0.blob",
    "length": 3,
    "index": {"pkg|lib/model.g.dart": {"offset": 0, "length": 3}}
  }
}
```

`updated_sources` lists source-tree logical IDs whose overlay content changed
since the last phase commit and `deleted_sources` the ones removed from it;
all four delta fields and `incremental` are required. When `incremental` is
true the worker may keep its Analyzer filesystem and library-cycle graph and
apply only those source changes, avoiding re-analysis of unchanged files.

`updated_cache` and `deleted_cache` describe changes under the artifact tree.
They refresh the worker's shared asset caches, and generated `.dart`/`.part`
files among them are also refreshed into the Analyzer's in-memory view —
the same handling source-tree changes get — because dependency packages can
emit Analyzer-visible generated sources there.

On an incremental reset the worker also diffs the directive sets
(`import`/`export`/`part`/`part of`/`library`) of committed `.dart` and
`.part` assets against what it recorded before; only a directive change
clears the cached library-cycle graph. If a worker cannot obtain an
incremental update it performs the full clean-build refresh instead.

`reset-overlay-blob-v1` is a required initialization capability. Rust rejects
workers without it. Every reset must explicitly contain `overlay_blob`, even
when null; older workers/messages cannot silently select legacy transport.

With multiple initialized workers, Rust writes one immutable blob per reset
under `<root>/.dart_tool/build_runner_accelerator/overlay-blobs`. The JSON
index maps the union of updated source/cache IDs with available overlay values
to contiguous, nonnegative byte offsets and lengths, in logical-ID order.
Missing values have no entry; deletion deltas have no payload. Empty values
and empty snapshots are valid. `length` is the complete blob byte length.

Rust creates a new file exclusively, writes every value, flushes and closes
it before notifying workers. No fsync is requested for this ephemeral IPC.
The owner retains the file until all parallel reset requests have joined,
then unlinks it on success or failure. Partial writes are closed and removed
without publishing a reset. No next reset/build/watch reuses a blob. Abrupt
termination can leave orphans; exclusive creation and explicit descriptors
prevent their reuse. Legacy per-asset spool files are ignored, not migrated
or purged. Cleanup errors are best effort.

Workers validate descriptor shape, absolute path, requested asset IDs,
contiguous bounds, complete coverage, exact file length and short reads.
They open once and seek/read indexed ranges rather than unconditionally
allocating a buffer for the whole file. Values are staged before phase-state
invalidation. Malformed, missing or incomplete transport fails the reset.
An updated ID absent from a valid multi-worker index removes its stale local
produced value and retains the existing full-refresh fallback if needed.

With one initialized worker, `overlay_blob` is null and the existing in-memory
produced-output path is retained without a spool file. Every updated ID must
have a value in the current Rust overlay; a missing value fails before any
worker reset is sent, preventing stale in-memory output reuse. With no
initialized workers, no reset is sent. Source/cache invalidation, resolver-use
deferred Analyzer notification, resident driver reuse, phase visibility, dependency
recording and atomic graph/output commit remain unchanged.
See [ADR 0027](../docs/adr/0027-reset-overlay-blob-transport.md).

The worker responds with the same `type` and `id`.

### build

```json
{
  "v": 1,
  "type": "build",
  "id": 2,
  "builder": "json_serializable:json_serializable",
  "kind": "normal",
  "instance_key": "opaque-action-instance-key",
  "input": "json_serializable_app|lib/model.dart",
  "phase": 3,
  "is_root": true,
  "blocked_assets": [
    "json_serializable_app|lib/model.json_serializable.g.part"
  ],
  "allowed_outputs": [
    "json_serializable_app|lib/model.json_serializable.g.part"
  ],
  "options": {},
  "triggers": []
}
```

`phase` is the globally resolved build phase for the action. `is_root` is the configured package-root bit passed to BuilderOptions; it is required and must be boolean. Kind, phase (a nonnegative integer),
non-empty instance_key, options, allowed_outputs and triggers are also required.
Only batch blocked_assets is inherited; missing fields do not select legacy
defaults. `blocked_assets`
is a logical-ID hint for the Dart adapter: it includes same/future normal
outputs, post-process outputs, and outputs hidden by the pending transaction.
The Rust asset RPC applies the same rule independently. The runtime expected-output mapping is normalized by the Dart manifest generator before this request is sent. An asset's
`build_to` location is not encoded in the logical ID; Rust resolves known
generated IDs to either the package path or the artifact tree cache.

`build_batch` carries the same `blocked_assets` list once on the outer batch
message. Child requests omit that field and inherit the batch list. A batch
must contain requests with the same phase and builder kind. The worker
advertises `shared-blocked-assets-v1` during initialization; this capability is
required for protocol v1.

## Dart to Rust

### asset_request

The worker may suspend a build action while it requests an asset operation.

```json
{
  "v": 1,
  "type": "asset_request",
  "id": 1000,
  "build_id": 2,
  "op": "read",
  "asset": "json_annotation|lib/json_annotation.dart",
  "phase": 3,
  "kind": "normal"
}
```

`build_id` identifies the active build item (`id` for a single build and the
zero-based item id for a batch). Rust uses its own `BuildRequest` for the
visibility decision and validates the worker-supplied `phase` and `kind` against
that request. A normal action cannot read an output produced in its own or a
later phase, and post-process outputs are not visible to normal actions. The
physical source/cache choice is resolved from the Rust action graph, so
package-path files do not shadow a known artifact-tree output with the same
logical ID.

Supported operations are `read`, `can_read`, `find_assets`, and `resolve_assets`. Rust answers with `asset_response` using the same request id.

When a request names the output of an `is_optional: true` builder, Rust may
send a nested `build` message before returning the `asset_response`. The Dart
worker runs that action in the same resident process and returns its normal
binary build result. Nested actions may issue their own asset requests; the
worker must keep the suspended outer action's IO context intact while the
nested action runs. This is advertised as `optional-builder-demand-v1`.

The worker must advertise `asset-rpc-binary-read-v1` and
`build-result-binary-v1` during `initialized`. Rust rejects initialization when
either capability is absent.

A successful `read` response takes one of two forms. When the asset's current
bytes live on the filesystem (package source or the artifact-tree cache), Rust
answers with a plain JSON `asset_response` carrying the absolute path and the
worker reads the file itself:

```json
{
  "v": 1,
  "type": "asset_response",
  "id": 1000,
  "ok": true,
  "path": "/absolute/path/to/asset.dart"
}
```

The visibility decision and the source-vs-artifact-tree resolution stay on the
Rust side; the worker must not guess locations itself. A `FileSystemException`
while reading a returned path is treated as `asset not found`.

Only bytes held exclusively in the in-memory overlay use a binary frame. Its
payload is:

1. 4 ASCII bytes `BRAB`
2. 4-byte metadata length, big endian
3. UTF-8 JSON metadata object of that length
4. raw asset bytes

The metadata has the following shape; `length` must equal the raw byte count.

```json
{
  "v": 1,
  "type": "asset_response",
  "id": 1000,
  "ok": true,
  "encoding": "raw",
  "length": 1234
}
```

Missing assets, errors, `can_read`, and `find_assets` continue to use JSON.
There is intentionally no JSON fallback for a worker that does not support the
binary read capability under this release-coupled contract.

`resolve_assets` is the batch form of `read`. The request carries an `assets`
list of logical asset ids instead of the single `asset` field:

```json
{
  "v": 1,
  "type": "asset_request",
  "id": 1001,
  "build_id": 2,
  "op": "resolve_assets",
  "assets": [
    "json_annotation|lib/json_annotation.dart",
    "meta|lib/meta.dart",
    "collection|lib/src/comparators.dart"
  ],
  "phase": 3,
  "kind": "normal"
}
```

Each entry is resolved under exactly the same rules as a `read` for that
asset — blocked assets and missing paths report `not_found`, in-memory
overlay bytes report `bytes`, and disk-backed assets report `path` — so a
`path`/`bytes` entry doubles as a positive `can_read` answer. The response
carries one positional entry per request asset:

```json
{
  "v": 1,
  "type": "asset_response",
  "id": 1001,
  "ok": true,
  "assets": [
    {"status": "path", "path": "/absolute/path/to/asset.dart"},
    {"status": "bytes", "offset": 0, "length": 1234},
    {"status": "not_found"}
  ]
}
```

When at least one entry is `bytes`, the response uses the same `BRAB` binary
frame as a binary `read`: the payload is the concatenated raw bytes of every
`bytes` entry in request order, and `offset`/`length` index into it. With no
`bytes` entries the response is plain JSON. The worker treats `not_found`
and malformed entries as unresolved and falls back to the sequential
`can_read`/`read` path for them, so a partial or failed batch answer can
never change build behavior.

### build_result

Successful `build_result` and `build_batch_result` responses always use one
`BRAR` binary frame. The payload is:

1. 4 ASCII bytes `BRAR`
2. 4-byte metadata length, big endian
3. UTF-8 JSON metadata object of that length
4. concatenated raw output bytes, in metadata order

For a single build result, the metadata has this shape:

```json
{
  "v": 1,
  "type": "build_result",
  "id": 2,
  "status": "success",
  "encoding": "raw",
  "outputs": [
    {"asset": "json_serializable_app|lib/model.g.dart", "length": 2}
  ],
  "deleted": [],
  "glob_reads": [],
  "reads": ["json_serializable_app|lib/model.dart"],
  "resolver_reads": ["json_annotation|lib/json_annotation.dart"],
  "resolver_entrypoints": ["json_serializable_app|lib/model.dart"],
  "resolver_used": true,
  "diagnostics": []
}
```

The raw bytes contain the bytes for each output in `outputs` order. The
`length` fields are consumed sequentially; their sum must equal the raw byte
count. Every build result requires `v`, outputs, deleted, reads, resolver_reads,
resolver_entrypoints, glob_reads, diagnostics and `resolver_used`; empty lists
are explicit. A batch also requires dep_graph, even when empty.
Every build result includes `resolver_used`, which reports whether
the action requested a `Resolver` from `Resolvers.get`. The Rust frontend and
Dart worker are shipped together, so the field is required.
`resolver_entrypoints` lists the assets the action registered as resolver
entrypoints through its input tracker; Rust expands them through the merged
dependency graph at dirty-check time, the same way stock build_runner uses
`phasedAssetDeps`. A batch result has
the same shape around a `results` array, plus a `dep_graph` object mapping
each resolved asset to its direct dependencies (`import`/`export`/`part`
targets); only entries reachable from that batch's entrypoints and not
already transmitted are included. The nested result outputs consume
the same raw byte stream in depth-first order:

```json
{
  "v": 1,
  "type": "build_batch_result",
  "id": 3,
  "encoding": "raw",
  "results": [
    {
      "v": 1,
      "type": "build_result",
      "id": 0,
      "status": "success",
      "encoding": "raw",
      "outputs": [{"asset": "app|lib/a.g.dart", "length": 10}],
      "deleted": [],
      "reads": [],
      "resolver_reads": [],
      "resolver_entrypoints": [],
      "resolver_used": false,
      "glob_reads": [],
      "diagnostics": []
    }
  ],
  "dep_graph": {"app|lib/a.dart": ["app|lib/a.g.part"]}
}
```

`outputs[].bytes` is not present in the binary metadata. JSON
`build_result`/`build_batch_result` responses are rejected; there is no
development-time compatibility fallback. Error responses and asset requests
whose result is not a successful raw-byte read continue to use JSON.

Both endpoints apply a 256 MiB safety limit to the complete frame, before
allocating the payload buffer. Chunking a larger result is not part of v1.

## Commit rule

Rust keeps returned outputs and pending deletions in overlays while later phases run. It writes
cache/source files and the graph only after every dirty action succeeds. A worker error therefore
leaves the previous committed output and graph intact; a pending deletion is visible to later
asset requests as a missing asset before the physical file is removed.
